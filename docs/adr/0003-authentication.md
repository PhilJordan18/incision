# ADR-0003 — Auth.js v5 with JWT sessions and application tables

- Status: **accepted for CP-04**, October 5, 2026, after an isolated spike (not merged). Real GitHub/Discord sign-ins are proven in CP-04.
- Requirements: AUTH-01, SEC-03, TEST-03; constrains SALLE-01, SEC-01, I18N-01. Choice D-14 (no email, separate accounts per provider).

## Context

AUTH-01 requires GitHub **and** Discord OAuth, and allows a local username/password (used by TEST-03). The project keeps no email address. The app runs one custom Node server (Next.js 16.3.7 + Socket.IO, ADR-0001) behind Azure's HTTPS front end (ADR-0002). The schema of CP-03 already holds `accounts` (our UUID, optional local login and password hash, no email) and `oauth_identities` (provider + provider subject → account).

Better Auth was not retained: its core user table requires an email.

## Decision

- **Library:** `next-auth@5.0.0-beta.32` (`@auth/core` 0.41.3), installed with `--save-exact` because it is a beta. Peer ranges accept Next 16 and React 19.
- **Sessions:** JWT strategy, **no database adapter**. Our tables are written by our own code from the callbacks.
- **Identity:** the `jwt` callback replaces the default token with `{ sub: <accounts.id> }`. For OAuth, the account is found or created from `account.provider` + `account.providerAccountId` (`oauth_identities`); `user.id` is a random value regenerated by Auth.js at each OAuth sign-in and must not be used. For Credentials, `authorize` returns our account id after verifying the scrypt hash.
- **No email anywhere:** GitHub with `scope: ""`, Discord with `scope: "identify"`, and both `profile()` overrides return only `{ id }`. The token holds only `sub`, `iat`, `exp`, `jti`; `/api/auth/session` exposes only `{ user: { id }, expires }`. OAuth access/refresh tokens are not kept. `debug` stays `false`, no custom `logger.debug`, and `profile`/`account` are never logged or persisted.
- **Origin:** `AUTH_URL` is required and equals `APP_URL`. Without it production answers 500 (`UntrustedHost`); `AUTH_TRUST_HOST` alone builds a wrong callback URL behind our custom server. With it, cookies are `__Secure-`/`__Host-`, `HttpOnly`, `Secure`, `SameSite=Lax`. `AUTH_SECRET` (≥ 32 random bytes) is required in production; rotation through `AUTH_SECRET_1..3`.
- **Sign-in starts** are CSRF-protected POSTs (`/api/auth/signin/<provider>`); built-in pages are English only, so `pages.signIn` and `pages.error` point to our localised pages (I18N-01).
- **Accounts per provider:** at the checkpoint, a GitHub sign-in and a Discord sign-in create two distinct accounts. No merge by name or email, no linking promised (D-14).

## Reading the session in Socket.IO

The handshake middleware decodes the session cookie with `getToken` (or `decode`) from `next-auth/jwt`, using the same secret(s) and the cookie name of the scheme: `__Secure-authjs.session-token` over HTTPS, `authjs.session-token` over HTTP (the name is also the decryption salt). A missing, tampered, wrongly signed or expired token (15 s tolerance) is refused; `socket.data` keeps the account id and `exp`. The identity is never `socket.id` nor a value sent by the client (ADR-0001).

## Consequences and obligations for CP-04

- **Expiry:** the default 30-day rolling session is too long for a school context; use a short `session.maxAge` (D-07 proposes 24 h).
- **Sign-out does not revoke a JWT:** a cookie captured before sign-out stays valid until it expires, and deleting the cookie does not close an open socket. CP-04 must (1) record `exp` at the handshake and disconnect or re-check it on events, (2) disconnect the account's sockets on sign-out (`events.signOut`), handing the event to the custom server through a process-wide value, as for the deployed commit, and (3) decide on revocation: short sessions only, or a per-account session version checked by the `jwt` callback and the socket guard (an additive column on `accounts`).
- **Logs:** failed credential sign-ins are logged with a stack trace; a custom `logger.error` logging only the error type avoids noise without leaking input.
- **Not yet proven:** real GitHub and Discord round trips (GitHub was exercised against a local mock with PKCE, Discord up to the provider redirect), sign-in through a server action, SameSite behaviour in a real browser.
