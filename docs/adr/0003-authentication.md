# ADR-0003 — Auth.js v5 with JWT sessions and application tables

- Status: **accepted**, October 5, 2026, after an isolated spike; **implemented in CP-04** (October 6). Real GitHub/Discord sign-ins are still to be proven locally and in production (manual procedure in [DEPLOYMENT.md](../DEPLOYMENT.md#authentication)); automated tests stop at the provider's authorisation URL.
- Requirements: AUTH-01, SEC-03, TEST-03; constrains SALLE-01, SEC-01, I18N-01. Choice D-14 (no email, separate accounts per provider).

## Context

AUTH-01 requires GitHub **and** Discord OAuth, and allows a local username/password (used by TEST-03). The project keeps no email address. The app runs one custom Node server (Next.js 16.3.7 + Socket.IO, ADR-0001) behind Azure's HTTPS front end (ADR-0002). The schema of CP-03 already holds `accounts` (our UUID, optional local login and password hash, no email) and `oauth_identities` (provider + provider subject → account).

Better Auth was not retained: its core user table requires an email.

## Decision

- **Library:** `next-auth@5.0.0-beta.32` (`@auth/core` 0.41.3), installed with `--save-exact` because it is a beta. Peer ranges accept Next 16 and React 19.
- **Sessions:** JWT strategy, **no database adapter**. Our tables are written by our own code from the callbacks.
- **Identity:** on sign-in, the `jwt` callback replaces the default token with our claims `{ sub: <accounts.id>, sessionVersion, authTime }` (Auth.js adds `iat`, `exp`, `jti`). For OAuth, the account is found or created atomically from `account.provider` + `account.providerAccountId` (`oauth_identities`); `user.id` is a random value regenerated by Auth.js at each OAuth sign-in and is not used. For Credentials, `authorize` returns our account id after verifying the scrypt hash.
- **No email anywhere:** GitHub with `scope: ""`, Discord with `scope: "identify"`. Both `profile()` overrides return only `{ id, name }`; the name only seeds the display name of a **new** account (`initialDisplayName`, D-14) and is never stored afterwards nor put in the JWT. `/api/auth/session` exposes only `{ user: { id }, expires }`. OAuth access/refresh tokens are not kept. `debug` stays `false`; the logger prints error types and wrapped error codes only, never messages, profiles, tokens or submitted credentials.
- **Origin:** `AUTH_URL` is required and equals `APP_URL`. Without it production answers 500 (`UntrustedHost`); `AUTH_TRUST_HOST` alone builds a wrong callback URL behind our custom server. With it, cookies are `__Secure-`/`__Host-`, `HttpOnly`, `Secure`, `SameSite=Lax`. `AUTH_SECRET` (≥ 32 characters, 32 random bytes recommended) is required in production. next-auth 5.0.0-beta.32 reads `AUTH_SECRET` only (its `AUTH_SECRET_1..3` rotation list is ignored by the Next.js integration): changing the secret signs everyone out.
- **Sign-in starts** from our pages through server actions (POST only; Next.js refuses an Origin that differs from the Host), which call Auth.js on the server; Auth.js' own POST endpoints keep their double-submit CSRF token. Session cookies are `SameSite=Lax`. Built-in pages are English only, so `pages.signIn`, `pages.error` and `pages.signOut` point to our localised pages (I18N-01).
- **Accounts per provider:** at the checkpoint, a GitHub sign-in and a Discord sign-in create two distinct accounts. No merge by name or email, no linking promised (D-14).

## Reading the session in Socket.IO

The handshake middleware reads only the Cookie header with `getToken` from `next-auth/jwt`, with `AUTH_SECRET` and `secureCookie` derived from the public URL: the cookie is `__Secure-authjs.session-token` over HTTPS and `authjs.session-token` over HTTP, and its name is also the decryption salt. Without a session cookie the socket is **anonymous** (no SQL; the smoke test's ping and future guests use it). A cookie that does not decrypt, has expired (15 s tolerance), is older than 24 h, belongs to a deleted account or carries a revoked version is **refused** (`UNAUTHORIZED`). `socket.data` keeps the account id, the version and the deadline. The identity is never `socket.id` nor a value sent by the client (ADR-0001).

## Sessions and revocation (CP-04, option B)

- **Lifetime:** `session.maxAge` 24 h, and every check refuses a session whose `authTime` is 24 h old: Auth.js re-issues the cookie when `/api/auth/session` is read (pages and actions never write it), but the session never outlives 24 h from sign-in (D-07). No "remember me".
- **Version:** `accounts.session_version` (integer, default 1, ≥ 1, additive migration `0001`). The JWT records the version read at sign-in. Every later read (`auth()`, `/api/auth/session`, Socket.IO handshake) compares it with the database; a mismatch, a missing account or a failed check refuses the session, and the version of an old JWT is never replaced by the current one. Requests without a session cookie never query the database.
- **Sign-out:** a protected server action increments the version in one statement (every session of the account ends, on every device) and closes the account's sockets through a process-wide registry shared by the Next.js bundles and the custom server (`globalThis`, single instance). The built-in `POST /api/auth/signout` is refused (405), because Auth.js would swallow a failed revocation and still clear the cookie; `events.signOut` only revokes a still-valid session, so an old revoked cookie cannot sign the account out repeatedly. If the database refuses the increment, the action reports the failure and keeps the session. A database outage makes protected pages and sockets refuse sessions (fail closed); the cookie is kept.
- **Sockets:** each authenticated socket is disconnected at its session's deadline and on revocation; protected events re-check expiry, revocation (in memory, after this process's sign-outs) and origin. A version changed or an account deleted outside the application (e.g. by SQL) is seen at the next handshake or HTTP request, not by an already open socket: a future in-app account deletion must also call `registry.revoke`.
- **Local credentials:** asynchronous scrypt (N=2^15, r=8, p=3, 16-byte salt, 32-byte key), stored as `scrypt$15$8$3$<salt>$<key>`; the parser checks every field, bounds the parameters and requires canonical base64url; the database checks the shape. Unknown logins cost a decoy derivation; failures give one generic error. Limits, in memory and counted before the first `await`: per 15 minutes, 5 failures per login and address, 50 per login, 100 failures and 200 checked attempts per address, and at most 3 checks at once, 2 per address (scrypt shares libuv's 4-thread pool with DNS and files); a server failure counts as nothing. The client address comes from the TCP peer or the last `X-Forwarded-For` entry of `TRUSTED_PROXY_HOPS` trusted proxies, set by the custom server in an internal header that overwrites any client value.

## Still not proven

Real GitHub and Discord round trips (the E2E tests stop at the authorisation URL; the spike exercised GitHub against a local mock with PKCE), behaviour behind Azure's front end (callback URLs, `X-Forwarded-For` format), and SameSite behaviour of real provider redirects in production.
